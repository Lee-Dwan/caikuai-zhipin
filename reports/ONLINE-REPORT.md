## 五、失败保护与通知机制

1. **采集失败保护**：单个数据源失败不影响其它数据源；失败机构的岗位保留上次成功数据，不判下架；线上仍展示完整历史。
2. **健康检查**：`success_rate < 60%` 或全部失败时，工作流标记为失败（红色），并在日志打出 `::error::`。
3. **失败通知**：失败时自动创建 GitHub Issue（标题含日期，正文带运行链接），同时 GitHub 会向仓库所有者发送失败邮件（Settings → Notifications 默认开启失败通知）。
4. **运行日志**：每次运行的完整日志保留在 Actions；`reports/latest.md` 与 `data/collect-report.json` 随数据一起提交，可追溯。
5. **数据原子性**：先写临时文件再替换，避免半截文件；`state.json` 只增不滥删，已下架岗位保留 120 天。

## 六、日常维护

- 改文案/样式/二维码：编辑 `index.html`、`assets/`，push 后 1 分钟内自动生效，网址不变。
- 加事务所：按 `MAINTAIN.md` 新增一个采集器文件，push 即可。
- 关停采集：删除或注释 `scripts/collectors/__init__.py` 中对应模块名。
- 查看更新：首页“最近更新”与仓库 commit 记录一致；Actions 页面可看每次运行。

## 七、已知限制（如实说明）

- 容诚在 GitHub 云端无法采集（官网限制境外 IP），云端每日成功率为 9/10；其历史岗位保留在线上，建议每月在本机（境内网络）手动执行一次 `python3 scripts/collect.py --firms rongcheng` 后 push，即可刷新。
- GitHub Actions 定时任务在整点高峰可能延迟数分钟至十几分钟启动，属平台调度行为。
- GitHub Pages 在国内的可访问性总体良好（本次实测 0.5 秒级），但作为境外平台仍存在政策波动风险；如后续出现访问异常，可在不改代码的情况下把同一仓库接到其它静态托管，页面无需改动。
